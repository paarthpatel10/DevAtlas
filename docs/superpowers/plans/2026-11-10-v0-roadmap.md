# DevAtlas V0 — Roadmap, Decisions, and Risks

**Spec:** `open_source_intelligence_v0_spec.md` (primary product and engineering specification)
**Detailed plan for the first milestone:** `docs/superpowers/plans/2026-11-10-m1-foundation-discovery.md`

This document is the overall plan for the whole V0. Each milestone gets its own detailed
task plan, written when the previous milestone ships. Every milestone leaves the app runnable
and demoable.

---

## 1. Repository inspection (2026-11-10)

- The repository contains only `README.md` and the spec. Two commits, remote `origin` → GitHub.
- There is no existing code or convention to preserve, so we scaffold from the spec's §7.4/§7.5 layout.
- Machine toolchain: Python 3.13 (via `py`/`uv` 0.12.5), Node 22.20 / npm 10.9. **No Docker, no
  local PostgreSQL, no Redis.** This drives decisions D1 and D2 below.

## 2. Milestones

Each milestone is a vertical slice that ends with a working, demoable app.

| # | Milestone | Spec phases | Demoable outcome |
|---|-----------|-------------|------------------|
| **M1** | **Foundation + end-to-end discovery** | 0, 1 (core), 2 (mock), 3 (core), 4 (core), 5 (core) | Developer types "I need X for a project using Y" → gets a short, evidence-backed shortlist from a real-repo seed dataset → opens detail page → saves it. Explore with keyword search + filters. |
| M2 | Explore & collections depth | 4, P1 collections | Explore sections (featured, by category), sort options, named collections with notes, add-to-collection from any card, richer detail page (maintenance signals, sources, related repos when evidenced). |
| M3 | Real AI + real ingestion | 1 (full), 2 (full) | Bedrock LLM + embedding providers behind the existing interfaces; LLM structured analysis with strict validation and prompt-injection guards; incremental refresh; paginated GitHub endpoints (Link-header pagination for releases and search-based discovery); curated list grown to ~300–1,000 repos; `POST /repositories/{o}/{n}/analyze` (dev only). |
| M4 | Ask AI depth + evaluation | 5 | LLM query understanding and reranking (mock path kept); clarifying questions; persisted conversations; recommendation feedback capture; a 50–100 query benchmark with P@5, Recall@5, MRR and NDCG@5 reporting; rate limits on AI endpoints. |
| M5 | Project-aware recommendations | 6 | Project CRUD (stack, requirements, constraints); recommendations that use project context; compatibility/integration explanations; saved recommendations per project. |
| M6 | Tech Radar, comparison, learning | 7 | Scheduled snapshot refresh; transparent trending/rising/emerging rules (growth claimed only when snapshots exist); Tech Radar page; 2–4 repo comparison; curated learning collections. |
| M7 | Hardening & deployment | 7, 8 | Accessibility/performance pass, observability, AWS deployment, architecture docs, demo script and screenshots, known limitations. |

The order follows the spec's guidance (§17): prioritize "describe a problem → useful
recommendations" over completing every screen.

## 3. Key technical decisions

| ID | Decision | Rationale |
|----|----------|-----------|
| D1 | **Hosted PostgreSQL + pgvector (Neon)** for dev and tests. A `docker-compose.yml` with `pgvector/pgvector:pg17` is still provided but not verified on this machine. | User choice: no Docker on this PC. Neon supports `CREATE EXTENSION vector`, HNSW, and full-text search. A Neon *branch* gives a separate test database. |
| D2 | **No Redis/Celery in V0.** Ingestion, analysis, and embedding run as idempotent CLI scripts (`python -m scripts.<name>`). | The spec allows "a simpler job runner for the first local version". External API calls stay out of the request path. Celery can be added in M3/M6 if scheduled refresh needs it. |
| D3 | Monorepo: `backend/` (FastAPI, uv-managed, Python ≥3.12) and `frontend/` (Next.js 16 App Router, TypeScript, Tailwind v4, shadcn/ui). | Spec §7.1, §19.6. |
| D4 | **Sync SQLAlchemy 2.0 + psycopg 3 + Alembic** (hand-written migrations). | Simpler than async for a modular monolith. FastAPI runs sync endpoints in a threadpool. Autogenerate does not handle `CREATE EXTENSION` or vector types well. |
| D5 | Keyword retrieval = Postgres FTS (`tsvector` column with weights A/B/C, GIN index). Semantic retrieval = pgvector cosine distance over summary + README-chunk embeddings, aggregated to the best chunk per repository. Fusion = RRF, `k` configurable (default 60). | Spec §6.3. |
| D6 | **AI provider abstraction** (`LLMProvider`, `EmbeddingProvider`) selected by `AI_PROVIDER`. M1 ships only the deterministic **mock** providers. Bedrock arrives in M3 behind the same interfaces. | Spec §11.1, §1.2.8. Demo mode must work without credentials. |
| D7 | Mock embeddings = **feature-hashed unigram+bigram vectors** (1024-dim, L2-normalized). Mock query understanding = **vocabulary-driven extraction** (`backend/data/vocabulary.yaml`). Mock analysis = **extractive only** (README text, never invented). | Deterministic, honest, and testable. The UI labels demo mode. Real semantic quality arrives with Bedrock embeddings. |
| D8 | **Seed data = a committed snapshot of real GitHub API responses** for ~70 curated repositories, built once by `scripts/build_seed_snapshot.py` and loaded idempotently by `scripts/seed_demo_data.py`. Metrics are shown with "Snapshot · <date>". | The spec forbids invented metrics. A snapshot gives real metadata and README evidence, and works offline afterwards. |
| D9 | Embedding column fixed at **1024 dims** (`EMBEDDING_DIM`). The `embedding_model` value is stored per row. Changing the model requires re-embedding (CLI). | Matches Titan Text Embeddings v2 default. The mock produces the same dimension. |
| D10 | Evidence status vocabulary: requirements are `evidenced` (with a source snippet) or `not_established`. Stack compatibility is `evidenced`, `inferred` (e.g. same language), or `not_established`. **No match percentages.** Transparent signals (keyword rank, semantic rank, RRF score) are shown instead. | Spec §6.5, §11.3, §20. |
| D11 | Auth: a single seeded **demo user** resolved by a FastAPI dependency (`get_current_user`). All user-owned tables carry `user_id`. | Spec §8.1. Real auth can replace the dependency later. |
| D12 | Third-party text (README, descriptions) is always rendered as **plain text** in the UI (never `dangerouslySetInnerHTML`). It is stored separately from generated analysis and never placed in prompts without untrusted-content framing (M3). | Spec §1.1.9, §11.2, §13. |
| D13 | Structured JSON logging via stdlib `logging` (no extra dependency); request-ID middleware; request-body size limit of 64 KB. | Spec §1.1.13, §13. |
| D14 | Tests: pytest. Pure-logic tests always run. DB tests are marked `db` and run only when `TEST_DATABASE_URL` is set (they are skipped, not failed, otherwise). Frontend: Vitest + Testing Library. | Keeps the suite runnable offline while still testing real Postgres behaviour. |

## 5. Dependencies

- **Backend:** fastapi, uvicorn[standard], pydantic, pydantic-settings, sqlalchemy≥2, psycopg[binary]≥3, alembic, pgvector, httpx, pyyaml. Dev: pytest, ruff. (M3: boto3.)
- **Frontend:** next 16, react 19, tailwindcss 4, shadcn/ui (Radix), lucide-react. Dev: vitest, @testing-library/react, @testing-library/user-event, jsdom, @vitejs/plugin-react.
- **External services:** a Neon Postgres project (dev branch + test branch). An optional `GITHUB_TOKEN` (any token with public read access) to build the seed snapshot quickly.

## 6. Risks and mitigations

| Risk | Impact | Mitigation |
|------|--------|-----------|
| Neon cold starts / network dependency | First request slow (~1 s); tests need internet | `pool_pre_ping=True`, short connect timeout, health endpoint reports `database: unavailable`, and the frontend shows a retryable error state. Pure-logic tests run offline. |
| GitHub unauthenticated limit is 60 requests/hour; the snapshot needs ~3 per repo | ~4 h to build the snapshot without a token | The builder is resumable (skips existing files) and stops cleanly on rate limit. Recommend `GITHUB_TOKEN`. |
| Mock "semantic" search is lexical, not semantic | Weaker relevance for vocabulary the dictionary does not know | Vocabulary expansion, a benchmark smoke test with an 80% hit@5 floor, and the UI labels demo mode. Real embeddings come in M3. The benchmark is tuned alongside the vocabulary, so it is a smoke test, not an unbiased evaluation. A held-out set comes in M4. |
| Committing third-party READMEs in the snapshot | Licensing/footprint concerns in a public repo | Store at most 40,000 chars per README, always link to the source, and keep attribution (repo URL, license). Revisit before any public launch: the snapshot can be git-ignored and rebuilt. |
| Prompt injection via README content (M3+) | LLM follows malicious instructions | M1 has no LLM in the path. M3 prompts frame content as untrusted, the LLM has no tools, and outputs are strictly schema-validated. |
| Library churn (Next 16, Tailwind 4, shadcn CLI) | Scaffold commands drift | Check current docs (Context7) at execution time and pin versions in lockfiles. |
| Windows-specific issues (encodings, paths, CRLF) | Garbled data (already seen once in `README.md`) | Always `encoding="utf-8"` in Python file I/O, `pathlib`, and `newline="\n"` for generated files. |

## 7. Deviations from the spec (kept current in the README)

1. **Database hosting:** Neon instead of Docker Compose for local development (Compose file still provided, unverified).
2. **No Redis/Celery:** ingestion and processing are CLI jobs (allowed by spec §7.1).
3. **Mock AI is lexical/extractive:** `problem_solved`, `use_cases`, and `limitations` show "Not established (demo analyzer)" until M3.
4. **Seed data** is a dated GitHub snapshot. Metrics are labelled with the snapshot date rather than "live".
5. **API surface:** `GET /repositories/facets` (categories, languages, licenses with counts) replaces `GET /repositories/categories`. `GET /me/saved` lists saved repositories.
6. **Curated `category` and `featured`** are stored on `repositories` (curator labels), separate from the generated `repository_analyses.category`.
7. **One current analysis per repository** (unique `repository_id`). Its version, model, and prompt version are stored, but history is not kept.
8. **M1 saves are a flat list.** Named collections with notes arrive in M2. Projects, conversations, feedback, relations, and Tech Radar tables are added in their milestones' migrations (users and ownership exist from M1).
9. **Explore search** uses AND keyword semantics and falls back to OR semantics when AND finds nothing, so natural phrases still return results.
